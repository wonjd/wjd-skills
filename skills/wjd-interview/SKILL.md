# 원정대 인터뷰

사용자를 인터뷰해서 `요청서.md` 한 장을 만든다. 목표는 하나다: 요청서를 받은 개발 담당이 요청한 사람에게 다시 물어볼 것이 없어야 한다.

사용자는 개발자가 아니고, 자기 업무는 가장 잘 아는 사람이다. 그래서 두 가지를 지킨다.

- **업무 말로 묻는다.** 서버, DB, API, 로그인 방식, 호스팅, 비용, 개발 일정은 묻지 않는다. 그것은 개발 담당이 정한다. 사용자에게는 "누가", "언제", "어떤 경우에"를 묻는다.
- **묻지 않은 것을 빼지 않는다.** 사용자가 말하지 않은 것은 "필요 없음"이 아니고 "아직 안 물어본 것"이다.

## 순서

1. **재료 읽기.** 지금 폴더의 파일을 본다.
   - `요청서.md`가 이미 있으면 아래 "이어서 하기"로 간다.
   - HTML은 `<script>`까지 읽어서 단추를 누르면 무슨 일이 일어나는지 파악한다. 화면 캡처, PDF, 글 파일도 읽는다.
   - 읽을 수 없는 형식(PPT, 엑셀)은 PDF로 저장하거나 화면을 캡처해서 넣어 달라고 한다.
   - 재료가 없으면 그대로 시작한다. 재료는 있으면 좋은 것이고 없어도 된다.
2. **첫 질문.** 본부와 맡은 업무, 그리고 무엇을 만들거나 고치려는지 묻는다. 이후 질문의 예시를 그 업무에 맞추기 위해서다.
3. **읽은 것 확인.** 재료가 있었다면 읽어 낸 내용을 다섯 줄 안팎으로 보여 주고 틀린 것이 있는지 묻는다. 프로토타입은 AI가 만든 경우가 많아서, 화면에 있는 동작이 사용자가 정한 것인지 AI가 임의로 채운 것인지 알 수 없다. 의심스러운 동작은 "의도하신 것이 맞습니까?"라고 짚어서 묻는다. (예: "시간이 겹쳐도 그대로 저장됩니다. 의도하신 것이 맞습니까?")
4. **인터뷰.** 아래 점검표에서 아직 확인되지 않은 것을 묻는다.
5. **짐작 확인.** 요청서를 쓰기 전에, 묻지 않고 짐작한 것을 전부 목록으로 보여 주고 확인받는다.
6. **요청서 쓰기.** 아래 형식으로 `요청서.md`를 지금 폴더에 저장한다.
7. **검토.** 아래 "검토"를 한 번 한다.
8. **마무리.** 파일 이름, 아직 못 정한 것, 재료와 다르게 해야 할 것만 짧게 알려 준다.

## 묻는 방법

- 한 번에 최대 4개만 묻는다. 한꺼번에 많이 물으면 사용자는 몇 개만 답하고 나머지는 사라진다.
- 선택지를 고르게 하는 질문 도구(AskUserQuestion)가 있으면 그것으로 묻는다. 없으면 번호를 붙인 글로 묻는다.
- 질문마다 추천 답을 하나 붙이고 이유를 한 줄로 적는다. 사용자가 "예"만 해도 진행되게 한다.
- 예시는 사용자의 본부와 업무에서 가져온다.
- 답이 새 질문을 낳으면 이어서 묻는다. (예: "팀장이 승인한다" → "팀장이 휴가면 누가 합니까?")
- 재료나 앞선 답에서 이미 확인된 것은 다시 묻지 않는다.
- 사용자가 "모르겠다"고 하면 누가 정할 수 있는지 묻고 "아직 못 정한 것"에 적는다.
- 폴더의 파일을 보면 알 수 있는 사실은 직접 찾아본다. 사용자에게는 결정만 묻는다.

## 점검표: 이것이 다 확인되어야 끝난다

항목마다 아래 넷 중 하나가 되어야 한다. 그 전에는 요청서를 쓰지 않는다.

- 사용자가 답했다
- 재료에서 읽었고 사용자가 맞다고 했다
- 못 정했고, 정할 사람을 적었다
- 사용자가 "해당 없음"이라고 했다

**목적**
- 지금은 이 일을 어떻게 하고 있고, 무엇이 불편한가
- 이것이 생기면 무엇이 달라져야 하는가

**사용자**
- 누가 쓰는가 (역할별로)
- 얼마나 자주, 어떤 상황에서 쓰는가

**화면과 동작**
- 어떤 화면이 있고, 화면마다 무엇을 하는가
- 단추를 누르면 무슨 일이 일어나는가 (저장, 상태 변경, 알림)
- 화면에 나오는 자료는 어디서 오는가 (직접 입력, 지금 쓰는 시스템, 엑셀)

**규칙**
- 계산하는 방법과 기준 (금액, 날짜, 기한, 한도, 횟수)
- 상태가 있다면 어떤 상태가 있고, 누가 언제 바꾸는가
- 알림은 누구에게 언제 가는가

**예외**
- 잘못 넣었을 때 고치기, 취소하기, 되돌리기
- 겹치거나 중복될 때
- 담당자가 없을 때 (휴가, 퇴사, 부서 이동)
- 기한이 지났거나 중간에 끝날 때
- 이미 있는 과거 자료는 어떻게 하는가

**권한**
- 누가 보는가 (본인, 팀, 본부, 전사, 경영진)
- 누가 만들고, 고치고, 지우는가
- 승인이 필요한가, 누가 승인하는가

스스로 "이 정도면 충분하다"고 판단해서 끝내지 않는다. 일찍 끝내는 경우는 사용자가 "여기까지"라고 말할 때뿐이다. 그때는 확인하지 못한 항목을 전부 "아직 못 정한 것"에 적고 요청서를 쓴다. "이번 범위에서 뺀다"고 임의로 적지 않는다.

## 요청서 형식

한 쪽 분량으로 쓴다. 개발 용어를 쓰지 않는다.

재료가 이미 보여 주는 화면은 다시 글로 옮기지 않고 파일 이름으로 가리킨다. 재료에 없는 것과 재료와 다르게 해야 할 것만 적는다. 재료가 없으면 화면과 동작도 글로 적는다.

```markdown
# 회의실 예약 요청서
- 본부·업무: 경영지원 / 회의실 관리
- 재료: 회의실예약.html (동작까지 읽음)
- 상태: 인터뷰 끝남 (못 정한 것 1개)

## 1. 목적
회의실이 겹쳐 잡히는 일을 없앤다. 지금은 웍스 대화방에 글로 예약한다.

## 2. 사용자
- 전 직원: 예약하고 자기 예약을 고친다.
- 경영지원 담당: 모든 예약을 고치고 지운다.

## 3. 화면과 동작
회의실예약.html 참고. 아래는 다르게 해야 한다.
- 시간이 겹치면 저장하지 않고 알려 준다. (재료는 겹쳐도 저장됨)
- 예약자는 직접 적지 않고 접속한 사람 이름이 들어간다.

## 4. 규칙
- 한 번에 최대 2시간, 30분 단위.
- 매주 반복 예약은 최대 4주.

## 5. 예외
- 외부 손님 미팅이면 경영지원 담당이 기존 예약을 옮길 수 있다. 옮기면 원래 예약자에게 알린다.

## 6. 권한
| 누가 | 보기 | 만들기 | 고치기·지우기 |
|---|---|---|---|
| 전 직원 | 전체 | 가능 | 자기 것만 |
| 경영지원 담당 | 전체 | 가능 | 전체 |

## 7. 아직 못 정한 것
- 예약하고 오지 않으면 자동으로 취소할지 (정할 사람: 경영지원 본부장)
```

"상태" 줄은 `인터뷰 끝남` 또는 `인터뷰 중 (여기까지)`로 적는다.

## 검토

요청서를 저장한 뒤, 이 대화를 보지 않은 다른 에이전트(Agent 또는 Task 도구)에게 요청서와 재료만 읽게 하고 이렇게 시킨다.

> 당신은 이 요청서대로 만들어야 하는 개발 담당이다. 만들기 시작하기 전에 요청한 사람에게 꼭 물어봐야 하는 것을 최대 5개 적어라. 개발 방법은 당신이 정하는 것이므로 묻지 않는다. 업무 규칙, 예외, 권한에서 빠진 것만 적는다. 없으면 없다고 답한다.

나온 질문 가운데 타당한 것을 사용자에게 묻고 요청서를 고친다. 검토는 한 번만 한다. 그런 도구가 없으면 스스로 개발 담당 입장에서 요청서만 다시 읽고 같은 일을 한다.

## 이어서 하기

`요청서.md`가 이미 있으면 그것을 읽고, "아직 못 정한 것"과 점검표에서 비어 있는 항목부터 묻는다. 이미 정한 것은 다시 묻지 않는다.

## 하지 않는 것

프로토타입을 고치거나 새로 만들지 않는다. 사용자가 요청서를 본 뒤에 따로 시키면 그때 한다.
